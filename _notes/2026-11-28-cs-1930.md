Git은 버전 관리 시스템이다. 물론 다른 버전 관리 시스템도 많지만, Git은 그중에서 가장 유명하고 인기 있다. 나도 매일 쓰다시피 하지만 누군가가 Git에 대해 물어봤을 때는 이렇게 답할 수밖에 없다. 
> 그냥 git init 하고 git add . 한 뒤에 git commit -m "커밋 메시지" 치면 돼요.

이것은 Missing Semester 가 꼬집은 내용이다. 과연 Git은 어떻게 동작할까? 그 내부 동작부터 하나씩 알아보자. 우선 Git의 컨셉츄얼한 부분부터 보자. Git은 파일을 blob, 디렉토리를 tree 라고 부른다. 또한, 이 tree에 대한 tree도 존재한다. 그리고 이 모든 변경 사항들을 그때마다 찍어서 저장하는 스냅샷 방식을 사용한다. 이렇게 찍힌 스냅샷과 SHA-1 해시를 갖고 있는 상태를 commit이라고 한다. blob, tree, commit을 한데 모아 object 라는 이름으로 부른다. object로 묶어 각자를 저장하고 로드할 수 있게 한다.

위 기본 구조를 기반으로 Git은 작업 사이의 관계를 맺는다. 한 커밋이 있고, 그 커밋 위에 새로운 커밋을 만든다고 해보자. 이때, 새롭게 생긴 커밋은 이전 커밋의 해시 값을 갖고 있는다. 해시값은 결정론적이고 하나만 가질 수 있기 때문에 이전 작업과의 관계가 성립된다. 여기에 더해 reference 라는 것이 존재한다. 이는 Git에서 각자의 작업을 별도로 할 수 있도록 나눠둔 것으로, 브랜치의 역할이 된다.

이렇게 커밋을 쌓다가 누군가가 나의 커밋을 그대로 가져가 새로운 작업을 진행해 별도의 커밋을 올렸다고 해보자. 그렇다면 작업은 두 갈래로 갈라질 것이다. 하지만 결국엔 하나의 결과물만 나와야 하므로 이를 합쳐야 한다. 이 과정을 merge라고 한다. 이때 합치는 방법은 간단하다. merge 커밋은 이전 커밋 2개의 해시 정보를 둘 다 들고 있고, 변경된 파일에 대해 작업의 기록을 본다. 최초 갈라진 지점에서 확인한 기록들을 뒤져가면서 알아서 합쳐준다. 이때, 같은 파일의 근처 위치를 건드리게 되면 그때는 merge conflict 라는 상황이 발생한다. Git이 알아서 해주던 merge 작업 중 사용자의 판단이 필요하다고 느끼고 충돌이 났다고 알려주는 것이다.

스냅샷은 변경되지 않는다. 각각의 스냅샷은 불변성을 지니고 있다. 이 불변성 때문에 append-only한 구조를 갖게 된다. 그렇기 때문에 파일 수정이 아닌 revert 라는 방법을 통해  수정을 처리한다. 하지만 이 방법을 사용하더라도 보안적으로 문제가 될 수 있는 중요 key 값을 올리게 되면 단순 Git으로 전부 처리할 수는 없다. 아무리 파일을 업데이트해도 이전 버전에서 이미 받은 로컬 파일이 존재할 수 있기 때문이다. 따라서 이때는 key 값을 무효화시켜야 한다.

앞서 나온 이야기들을 총정리해 pseudocode로 표현하면 아래와 같다.

```
type blob = array<byte> // 파일은 byte 형태로 저장된다.
type tree = array<string, tree | blob> // tree 구조가 단순히 blob만 대상으로 하는 게 아니라 tree도 대상으로 할 수 있다. 폴더 아래는 파일이 올 수도 폴더가 올 수도 있기 때문이다. string은 이름이다.
type commit = struct {
  snapshot = tree // tree가 
  parents = array<commit> // 바로 이전의 부모 커밋들에 대한 정보를 지닌다.
  actor = string // 작성자
  message = string // 메시지
}
type object = blob | tree | commit // object는 세 타입을 합쳐 처리하도록 만든 타입이다.
objects = map<string, object> // string 은 SHA-1으로 된 해시 값이다.
```

다음 글에서는 실제 git을 사용해보고 엮어서 이해를 높여보겠다.
